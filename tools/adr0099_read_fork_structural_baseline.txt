# ADR-0099 CHECK N1 — FROZEN baseline of D1 STRUCTURAL read-forks.
# Format: <path>|<fn>.  Enforced by tools/cut_gate_read_fork.sh as an EXACT SET:
# an ADDED entry is a new fork and goes RED; a STALE entry (fixed or renamed) also
# goes RED, so the file cannot decay into names that no longer mean anything.
#
# ── WHAT THIS FILE IS, AND WHAT IT IS NOT ──
# The read-fork scanner keyed off NAMES until 2026-07-28: a list of read-helper
# names and a list of enclosing-fn names. FOUR instances of one bug class shipped
# through that hole (#40 render, #41 modification base, #42 auto-email, E1) because
# the same defective SHAPE under an UNLISTED name was invisible. The scanner now
# detects the shape itself — a fresh live-DB opener bound to a local whose handle
# (or a derivative) is read through, under ANY fn name.
#
# Switching that on found 28 PRE-EXISTING forks. TWELVE are live in-serve on the
# serve-held tenant DB — the exact defect class, never before visible to any gate.
#
# 2026-07-28 (D1a, pre-cut v2.33.2 adversarial): 33, of which THIRTEEN are live
# in-serve. The D1 shape rule was recognised only in line-local forms, so a call
# rustfmt had WRAPPED across lines read as clean — meaning the rule's reach depended
# on the character length of the callee's path. Five more pre-existing forks were
# hiding behind that, one of them live in-serve. See the scanner header (D1a).
# Migrating them is product work (each is a read-path change on live routes, several
# on the invoice/NAV path) with its own review; it is deliberately NOT done in the
# detector-hardening change that found them. So this file FREEZES them.
#
# `CHECK N1 ✓ 0 new` therefore means "no fork was ADDED". It does NOT mean the tree
# is fork-free. The 28 below are OPEN. Nothing here is an exemption, an allow-list,
# or a claim of coherence — it is a debt register with teeth on additions.
#
# NEVER add a line here to make the gate pass. A new hit means a NEW fork: route the
# read through the shared Handle (`state.db.read()`/`.write()` → `try_clone`).
# Lines are removed only when the fork is actually migrated, in that same change.
#
# Verdicts below are from the 2026-07-28 triage (call sites checked, not inferred).

# ── GROUP A — LIVE IN-SERVE on the serve-held DB. ***EMPTY as of 2026-08-12.*** ──
# A second DuckDB instance co-resident with serve's Handle. Under H3 checkpointing
# is disabled, so anything the Handle has written is WAL-resident and these read the
# last-checkpointed SUBSET — the identical primitive behind #40/#41/#42/E1.
#
# ADR-0110 D8 swept the last eleven. GROUP A now contains ZERO entries: no in-serve
# request route or in-serve daemon opens its own connection to the tenant DB.
#
# READ THIS BEFORE ARMING THE D7 FENCE. "GROUP A is empty" is a claim about THIS
# list, and this list is what a STATIC scanner can see. Two known gaps survive it:
#   1. GROUP B below — separate-process CLI one-shots. They cannot borrow serve's
#      in-process Handle, and several run against a LIVE serve today. Their closes
#      fold the same WAL. See adr/adr-0110-*.md §"D8 — the CLI-opener class (N7)".
#   2. The factory split the scanner header already documents (an opener in one fn,
#      the read in its caller) — the SERVE_HANDLE_LIVE runtime tripwire's job.
# Arming the fence against a folded WAL that a CLI caused converts a silent bug into
# a money-path outage just as surely as an in-serve opener would. D8 removes the
# in-serve half of that precondition, not the whole of it.
#
# ── D2c CLOSED (2026-08-12) — the two mark-paid billing readers are MIGRATED ──
# `read_invoice_currency` and `read_invoice_total_gross_minor` stood here as "the
# twin of `read_base_currency`, which is PINNED and already Handle-routed" and "the
# D2a shape verbatim". Both now take the caller's `state.db.read()` connection, so
# their lines are REMOVED from this baseline in the same change (per the header's
# exact-set rule) and both names are now PINNED in adr0099_read_fork_scan.awk —
# re-introducing either opener reds CHECK N on the pinned rule, not just CHECK N1.
# Baseline count 33 → 31.
#
# ── D8 STEP 1 (2026-08-12) — the three NAMED in-serve readers are MIGRATED ──
# `calibration_overview_request`, `resolve_recipient_email` and
# `handle_quote_pipeline_status` are the exact three the ADR-0110 D7 fence tests
# name as "live GROUP-A openers on this head" — the reason `wal_fence_enabled`
# ships DISARMED. All three now read `state.db.read()` (the owned try_clone that
# holds no lock, so it moves into `spawn_blocking` unchanged), so their lines are
# REMOVED here per the header's exact-set rule. Baseline count 31 → 28.
# ── D1a (2026-07-28, pre-cut v2.33.2 adversarial) ──
# `handle_relay_send_email` is `POST /api/internal/send-email` — a LIVE in-serve
# route (deprecated, but it warns and serves rather than 410-ing). Inside its
# `spawn_blocking` it does `duckdb::Connection::open(&state.db_path)` and hands the
# connection to `email_relay_queue::insert_queued(…)`, a call rustfmt wraps across
# lines — which is exactly why D1 could not see it. It is co-resident with the shared
# Handle (the very next block uses `state.db.clone()`), and it WRITES, so it is a
# write-fork too. Its sibling READERS of the same table — `handle_list_email_relay_
# queue` and `handle_get_email_relay_row`, both in GROUP A above — were already
# frozen: a fused family (CLAUDE.md rule 14) split in half by a formatting accident.
# Migrating it is product work on a live route; frozen here, not silenced.
#
# ── D8 STEP 2 (2026-08-12) — the relay-queue family is MIGRATED, WHOLE ──
# The split D1a described is closed the only way rule 14 allows: all THREE at once.
# `handle_relay_send_email` writes through `state.db.write()` (guard drop lockstep-
# syncs the mirror) and both sibling readers read `state.db.read()`. Removed here:
# `handle_relay_send_email`, `handle_list_email_relay_queue`,
# `handle_get_email_relay_row`. Baseline count 28 → 25.
# ── D8 STEP 3 (2026-08-12) — the Financial Report is MIGRATED ──
# `reports::compute_financial_report` was the WORST single site in GROUP A: FOUR
# independent instances on the live tenant path (two `Connection::open`, one
# `DuckDbBillingStore::open`, one `Ledger::open`) — and only ONE of the four was
# ever visible to this scanner. Opening the Financial Report, or the workshop
# dashboard tile that reuses it, was on its own enough to fold the serve Handle's
# WAL. It now takes `&aberp_db::Handle`: a scoped `write()` for the idempotent
# schema bootstrap, then `read()` try_clones for the SQL aggregates and the
# ledger walk. Baseline count 25 → 24.
# ── D8 STEP 4 (2026-08-12) — the pdf-rerender daemon is WHOLLY on the Handle ──
# `prepare_rerender` was the daemon's last fresh-open family: it read pricing-job
# artifacts a co-resident in-serve writer had left WAL-resident, so it could see a
# just-priced quote as artifact-less and classify it PERMANENTLY failed (no retry,
# customer never gets the stock-alert PDF) — while its close truncated the WAL
# under the daemon's own `write_audit`. Migrated; the `QuotePdfRerenderDaemonDeps.
# db_path` field that existed solely to feed it is DELETED (rule 12), so the
# half-migrated state that made this possible cannot be reconstructed by accident.
# ── D8 STEP 5 (2026-08-12) — the DÁP/QES audit chain is MIGRATED, as a PAIR ──
# `serve::spawn_dap_audit_chain` (the boot service-session open + crash recovery)
# and `audit_dap_boot::run_heartbeat_supervised` (the anchor actor) are ONE family
# and moved together. The heartbeat was the worst shape in the whole census: it
# re-opened a foreign `Ledger` ON A TIMER for the life of the process, so on a
# `dap_enabled` tenant the WAL was folded every `audit_anchor_heartbeat_seconds`
# — the loss primitive re-armed on a schedule. Both now build the `Ledger` from a
# `try_clone` of the shared WRITE guard (the anchors are appends), so the DÁP
# chain is serialized with every other Handle writer. Baseline count 24 → 22.
# `write_one` also APPENDS (write_mes_adapter_event) through its fresh connection,
# so it is a WRITE-fork too — yet CHECK 10M reports ZERO, because its append-token
# set does not know that helper name either. Same name-list failure, other gate.
#
# ── D8 STEP 6 (2026-08-12) — the MES ledger writer is MIGRATED ──
# One append per shop-floor scan, each through its own `Connection::open` — the
# highest-FREQUENCY instance of the primitive in the tree. It now takes the shared
# `db.write()` guard for the whole tx (`aberp-mes` gains an `aberp-db` dep for it),
# and `MesBootDeps.db_path` / `LedgerWriterDeps.db_path` are DELETED, since each
# existed only to feed this fork.
#
# The migration is self-proving: the writer's own end-to-end test polled the row
# back through a fresh `Connection::open`. Once the write rode the Handle that
# poller read ZERO forever (checkpointing is disabled under H3, so the row is
# WAL-resident) — so the test HAD to move to `db.read()` in the same change, which
# is rule 14 demonstrated rather than asserted.

# ── GROUP C — NOT the serve-held live path. No fork; the shape rule cannot tell.
# A static shape scanner sees `Connection::open(x)`; it cannot see WHICH file `x` is
# or whether serve's Handle exists yet. These are the cases where that matters. The
# discriminator they all have is runtime, not textual — which is exactly what the
# SERVE_HANDLE_LIVE tripwire provides, and it stays silent on every one of them.
# ── serve.rs|run — RE-TRIAGED 2026-08-12 (ADR-0110 D8 / F1). READ THIS. ──
# This line used to read: "`provision_atomic`, at boot, BEFORE the shared Handle is
# opened." That justification was FALSE, and it hid three live openers.
#
# `run()` is not a boot phase. It is a ~2000-line function that SPANS the Handle
# open (`open_tenant_handle`, ~:1633) and keeps going for hundreds of lines after
# it. So "run is boot, therefore pre-Handle" is a category error: it exempted the
# whole function on a property only its FIRST HALF has. Three post-Handle openers
# lived in the second half behind that sentence —
#   ~:2390 cad-blob key provision AUDIT WRITE
#   ~:2432 quote_pricing_jobs secondary-index DDL
#   ~:2487 quote_pricing_jobs boot row count — ran on EVERY boot
# each folding the live Handle's WAL after the Handle had already written. With the
# D7 fence armed, the third would have fired `WalVanished` on the FIRST money-path
# `durable_ack` of every serve session. All three are MIGRATED onto `st.db`.
#
# THE INVARIANT THIS ENTRY NOW ENCODES — it is a LINE-REGION exemption, not a
# function exemption. Exempt: openers in `run()` BEFORE `open_tenant_handle`
# (currently ~:1206–:1461 — the billing/products/partners boot migrations and
# `provision_atomic`, which genuinely precede the Handle's existence).
# NOT exempt: ANY opener in `run()` after that call. There is no Handle-less window
# there, so such an opener is a GROUP-A fork wearing a boot-shaped costume.
#
# WHY THIS ENTRY CANNOT BE THE DETECTOR, and what is:
# this baseline is keyed per FUNCTION, so it physically cannot distinguish the two
# halves of `run()` — the entry stays "live" as long as ANY opener remains in the
# fn, which is why removing the three post-Handle ones did not even make it go
# STALE. The per-OPENER fingerprint set (tools/adr0098_prod_opener_fingerprints.txt)
# is the detector with the right granularity: it carried all three as distinct
# `run:duckdb::Connection::open(&…)` lines and went RED when they were removed.
# Where the two disagree about `serve.rs|run`, THE FINGERPRINT SET IS AUTHORITATIVE.
# Same lesson as `compute_financial_report`, where a per-fn view saw 1 of 4 openers.
#
# HOW TO RE-VERIFY (reproducible; this is how "GROUP A is empty" was re-derived on
# 2026-08-12 rather than read off a governance file):
#
#   h=$(grep -n 'let db_handle = open_tenant_handle' apps/aberp/src/serve.rs | cut -d: -f1)
#   awk -f tools/adr0098_opener_scan.awk apps/aberp/src/serve.rs \
#     | awk -F: -v h="$h" '$1+0 > h+0'
#
# ⚠ THE TRAP, and it WILL catch you: that check reports the DEFINITION line, and
# the discriminator is the CALL SITE. `record_upgrade_snapshot_mismatch_audit` is
# DEFINED at ~:6430 (far past the Handle open) but its only non-definition caller
# is at ~:1127, which is pre-Handle — so it prints as a false positive. Conversely
# a helper defined at the top of the file and called from a post-Handle boot arm
# would print as a false NEGATIVE, which is the dangerous direction. Always resolve
# the call site before judging. Both fns were checked this way, not by line order.
#
# So: before trusting this line again, diff the fingerprint set's `serve.rs|run:`
# entries against the pre-`open_tenant_handle` region. Do not extend this exemption
# to a new opener without checking which side of :1633 its CALLER is on.
apps/aberp/src/serve.rs|run
