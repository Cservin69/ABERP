# ADR-0099 CHECK N1 — FROZEN baseline of D1 STRUCTURAL read-forks.
# Format: <path>|<fn>.  Enforced by tools/cut_gate_read_fork.sh as an EXACT SET:
# an ADDED entry is a new fork and goes RED; a STALE entry (fixed or renamed) also
# goes RED, so the file cannot decay into names that no longer mean anything.
#
# ── WHAT THIS FILE IS, AND WHAT IT IS NOT ──
# The read-fork scanner keyed off NAMES until 2026-07-28: a list of read-helper
# names and a list of enclosing-fn names. FOUR instances of one bug class shipped
# through that hole (#40 render, #41 modification base, #42 auto-email, E1) because
# the same defective SHAPE under an UNLISTED name was invisible. The scanner now
# detects the shape itself — a fresh live-DB opener bound to a local whose handle
# (or a derivative) is read through, under ANY fn name.
#
# Switching that on found 28 PRE-EXISTING forks. TWELVE are live in-serve on the
# serve-held tenant DB — the exact defect class, never before visible to any gate.
# Migrating them is product work (each is a read-path change on live routes, several
# on the invoice/NAV path) with its own review; it is deliberately NOT done in the
# detector-hardening change that found them. So this file FREEZES them.
#
# `CHECK N1 ✓ 0 new` therefore means "no fork was ADDED". It does NOT mean the tree
# is fork-free. The 28 below are OPEN. Nothing here is an exemption, an allow-list,
# or a claim of coherence — it is a debt register with teeth on additions.
#
# NEVER add a line here to make the gate pass. A new hit means a NEW fork: route the
# read through the shared Handle (`state.db.read()`/`.write()` → `try_clone`).
# Lines are removed only when the fork is actually migrated, in that same change.
#
# Verdicts below are from the 2026-07-28 triage (call sites checked, not inferred).
